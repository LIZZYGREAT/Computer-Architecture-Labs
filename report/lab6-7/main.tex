\reportsection{一、实验目的}
本次实验是在前面已经完成的五级流水线 CPU 上继续添加指令。之前 Lab3--Lab5 已经能够执行基本的 MIPS 指令，并处理流水线中的数据相关问题。Lab6 需要继续支持算术逻辑、乘除法和 HI/LO 寄存器操作；Lab7 则增加转移指令，以及字节、半字和非对齐访存指令。

我这次主要想完成三件事：一是让新增指令能正确译码和执行；二是保证它们不会破坏原来已经实现的阻塞和数据前递；三是使用 Vivado 仿真，通过课程功能测试、参考 CPU 的写回记录和一些针对性用例来检查结果。乘除法部分按照实验允许的方式使用 Xilinx IP 核实现。

\reportsection{二、实验环境与原有 CPU 结构}
实验环境使用 Windows、Vivado 2025.2 和 XSim，目标器件为 \code{xc7a200tfbg676-2}。沿用原来 Lab3 的 \code{mycpu_verify} 工程，设计顶层为 \code{soc_lite_top}，仿真顶层为 \code{tb_top}。Lab6 和 Lab7 的目录主要存放各自的功能测试程序，没有重新复制一套 CPU。

CPU 保留 IF、ID、EX、MEM、WB 五个流水级。执行指令时，IF 从指令存储器取指；ID 译码并读取寄存器；EX 进行运算、计算访存地址，或等待乘除法单元；MEM 取得数据存储器的结果；WB 将结果写回寄存器。原本的前递逻辑允许 ID 直接取得 EX、MEM 或 WB 中已经准备好的结果，如果数据还没有产生，则先暂停后续指令。

\repofigure{cpu_pipeline.png}{0.95}{五级流水线与新增的乘除法、转移及访存通路（结构示意图）}

本次改动主要涉及指令译码、执行和访存控制，并新增了 \code{hilo_unit.v} 处理多周期乘除法。ID 负责识别新指令及其操作数，EX 和 MEM 计算结果，控制总线把必要信息传到后续流水级。

\reportsection{三、Lab6：算术逻辑与乘除法指令}
\textbf{1. 算术逻辑指令的扩展。}

首先在 ID 阶段增加 \code{add}、\code{addi}、\code{sub}、\code{slti}、\code{sltiu}、\code{andi}、\code{ori}、\code{xori} 以及 \code{sllv/srlv/srav} 的译码。这里除了确定 ALU 要做哪种操作，还需要告诉相关检测逻辑，这条指令是否真的会读取 \code{rs}、\code{rt}，以及最终要写哪个寄存器。

立即数处理是这部分比较容易出错的地方。例如 \code{addi} 使用符号扩展，而 \code{andi/ori/xori} 使用零扩展。现有 EX 阶段用下面的方式选择第二个 ALU 操作数（节选自 \code{EXE_stage.v}）：

\begin{lstlisting}[language=Verilog]
assign es_imm_zero_extend = es_src2_is_imm &&
    (es_alu_op[4] || es_alu_op[6] || es_alu_op[7]);
assign es_alu_src2 = es_src2_is_imm ?
    (es_imm_zero_extend ? {16'b0, es_imm} :
                          {{16{es_imm[15]}}, es_imm}) :
    es_src2_is_8 ? 32'd8 : es_rt_value;
\end{lstlisting}

可变移位指令还要把移位量改成从寄存器 \code{rs} 的低 5 位取得，被移位数据仍来自 \code{rt}。例如移位量为 31 时，只看低 5 位，算术右移还必须保留符号位。相关操作在 ALU 中通过移位和符号扩展来完成。

我们另外使用了一组短指令程序检查这些情况。比如 \code{andi r12,r5,0x8000} 的正确结果为 \code{0x00008000}，\code{xori r14,r5,0xffff} 得到 \code{0xFFFF0000}；可变算术右移的测试也得到了正确的符号扩展结果。下图按参考 CPU 的寄存器写回记录整理了几个关键值，能够直接观察不同运算的输出。

\repofigure{alu_key_values.png}{0.93}{算术逻辑定向用例的关键寄存器写回结果（来自匹配的参考 trace）}

\textbf{2. 乘除法 IP 与 HI/LO 寄存器。}

MIPS 的乘除法结果通常放在 HI 和 LO 两个特殊寄存器中。乘法把 64 位乘积的高 32 位放入 HI、低 32 位放入 LO；除法把余数放入 HI、商放入 LO。之后由 \code{mfhi/mflo} 读取，也可以用 \code{mthi/mtlo} 直接修改对应寄存器。

实现时新增了 \code{hilo_unit.v}，调用 Vivado 生成的乘法与除法 IP。乘法使用 33 位有符号扩展后的乘法器，兼顾有符号和无符号的 32 位乘法；除法器本身是无符号运算，有符号除法先取得两个操作数的绝对值，算出商和余数后再恢复符号。

乘除法不能像普通加法一样每个周期都得到结果，所以 EX 阶段需要等待。这里使用的主要控制信号是 \code{start}、\code{busy}、\code{done} 和 \code{consume_done}。实际流水线中关键控制代码如下：

\begin{lstlisting}[language=Verilog]
assign es_hilo_start = es_valid && es_hilo_multdiv &&
                       !es_hilo_busy && !es_hilo_done;
assign es_hilo_consume = es_valid && es_hilo_done && ms_allowin;
assign es_ready_go = !es_hilo_multdiv || es_hilo_done;
assign es_allowin = !es_valid || (es_ready_go && ms_allowin);
assign es_to_ms_valid = es_valid && es_ready_go;
\end{lstlisting}

它的执行过程可以简单概括为：

\begin{lstlisting}[language={}]
EX 接收乘除法指令，锁存输入操作数
发出一次乘除法请求
while 结果尚未完成:
    EX 保留当前指令，不接收下一条
    IF、ID 根据 allowin 信号等待
结果有效后，更新 HI、LO
当前指令允许进入后一级，只消费一次结果
\end{lstlisting}

除法 IP 有两路输入（被除数和除数），需要它们在同一次握手中被正确接收。为此，在 \code{HILO_DIV_SEND} 状态下保持两路有效信号和输入值，直到两路 \code{ready} 同时成立，再等待结果返回，避免除法请求重复或只提交一半输入。

\repofigure{hilo_handshake.png}{0.82}{HI/LO 单元请求、等待、完成与消费的状态关系（流程示意图）}

在单元级测试中，共接受 3 次乘法和 4 次除法请求，完成并提交 6 次；还有一次进行中的除法被复位取消。测试也检查了 HI/LO 读写与完成状态保持，结果为 PASS。这说明单元的基本运算和握手能够按预期工作。

\reportsection{四、Lab7：转移指令与延迟槽}
本次在原有 \code{beq/bne/jr/jal} 等指令的基础上增加了 \code{j}、\code{jalr}、\code{bgez}、\code{bgtz}、\code{blez}、\code{bltz}、\code{bgezal} 和 \code{bltzal}。这些指令主要在 ID 阶段根据寄存器值计算是否跳转，以及跳转到哪个地址。

例如 \code{bgez} 判断 \code{rs} 是否大于等于 0；\code{bltz} 判断它是否小于 0。链接跳转的返回地址是当前 PC 加 8，这是因为实验采用的 MIPS 流水线保留一条延迟槽指令。分支决定跳转后，紧接着的一条指令仍然需要执行。

这里继续沿用原来的前递机制。若分支依赖前面指令写入的 \code{rs}，ID 可以取得已经产生的结果；遇到尚未准备好的值则需要等待。特别是 EX 正在执行较长的除法时，ID 即使已经算出分支目标，也不能反复发出跳转。RTL 中把跳转条件和当前指令是否能够推进联系起来：

\begin{lstlisting}[language=Verilog]
assign br_taken = (inst_j || inst_jal || inst_jr ||
                   inst_jalr || ds_branch_cond_taken) &&
                  ds_valid && ds_ready_go && ds_allowin;
\end{lstlisting}

为检查这部分，我们设计过一组“除法后立即执行分支”的短程序：先令 \code{r1=-23}、\code{r2=5}，执行有符号除法，再执行一条恒成立的 \code{beq}。从参考 trace 与 DUT 全部匹配的写回记录中可以看到：延迟槽将 \code{r3} 写为 \code{0x55}，跳过路径没有出现 \code{r4} 写回，跳转目标处 \code{mflo} 和 \code{mfhi} 分别读出了 \code{-4} 和 \code{-3}。这与预期执行顺序一致。

\repofigure{div_branch_retirement.png}{0.91}{除法后分支测试中实际出现的写回顺序（退休 trace 图）}

\code{jalr} 也单独检查了链接地址和延迟槽。例如定向用例在 \code{PC=0xBFC000E4} 执行 \code{jalr r26,r25}，得到 \code{r26=0xBFC000EC}，也就是 PC+8；随后的延迟槽写回 \code{r4=0x61}，跳转目标为 \code{0xBFC000F0}，原本需要跳过的路径没有产生写回。

\repofigure{jalr_retirement.png}{0.91}{JALR 的链接、延迟槽与目标路径写回记录（退休 trace 图）}

\reportsection{五、Lab7：字节、半字和非对齐访存}
前面的 CPU 主要实现 \code{lw/sw}，每次读写一个完整的 32 位字。本次新增 \code{lb/lbu/lh/lhu}, \code{sb/sh} 和 \code{lwl/lwr/swl/swr}，需要在保留原有同步 RAM 的情况下处理不同的访存宽度。

我们的数据 RAM 以 32 位字为单位，实际的字节位置由地址低两位决定。例如小端存储中，地址最低两位为 0 的字节放在读出数据的 \code{[7:0]}，偏移为 1 的字节放在 \code{[15:8]}。\code{lb} 需要把选中的字节进行符号扩展，\code{lbu} 则补零；半字的处理方法类似。MEM 阶段已有相应的数据选择逻辑，下面以 \code{lb} 的一部分为例：

\begin{lstlisting}[language=Verilog]
if (ms_mem_op[`MEM_OP_LB]) begin
    case (ms_alu_result[1:0])
        2'd0: mem_result = {{24{data_sram_rdata[7]}},
                            data_sram_rdata[7:0]};
        2'd1: mem_result = {{24{data_sram_rdata[15]}},
                            data_sram_rdata[15:8]};
        // offsets 2 and 3 use the higher byte lanes
    endcase
end
\end{lstlisting}

写入也要指定哪些字节可以改变。例如 \code{sb} 只使能一个字节通道，不能覆盖同一个字里的另外三个字节。EX 阶段实际代码如下：

\begin{lstlisting}[language=Verilog]
else if (es_mem_op[`MEM_OP_SB]) begin
    es_store_wen_r  = 4'b0001 << es_alu_result[1:0];
    es_store_data_r = es_rt_value <<
                      {es_alu_result[1:0], 3'b000};
end
\end{lstlisting}

这里 \code{es_store_wen_r} 是四位字节写使能，\code{es_store_data_r} 将要写的字节移到对应位置。\code{sh} 则使用两位写使能。

\code{lwl/lwr/swl/swr} 还要处理非对齐数据。其中 \code{lwl/lwr} 并不一定覆盖目标寄存器的全部 32 位，有一部分要保留旧的 \code{rt}。因此除了内存读出的字，还要把经过相关检测和前递的 \code{rt} 原值送到 MEM 阶段，按地址低两位合并。比如 \code{lwl} 偏移为 1 时，实际合并代码是：

\begin{lstlisting}[language=Verilog]
// From MEM_stage.v, LWL with address offset = 1
2'd1: mem_result = {data_sram_rdata[15:0],
                    ms_rt_value[15:0]};
\end{lstlisting}

\code{swl/swr} 则按照地址偏移生成不同的字节写使能和写入数据。这一部分最需要注意的是：内存访问的数据正确还不够，写入时不能破坏不应该修改的其他字节。

我们增加了专门的连续依赖测试，覆盖 \code{lw} 后立即执行字节/非对齐 store、load 后继续使用读出的数据、\code{lwl/lwr} 连续合并，以及 \code{lw} 后的条件分支。测试对 9 次 store 的实际地址、写使能和写数据进行检查，还检查了分支重定向次数。结果为 PASS，25 条写回记录全部匹配独立参考 CPU。

\reportsection{七、实验总结}
这次是在原来已经能够处理流水线冲突的 CPU 上继续扩展指令，修改范围比前面单独添加几条 ALU 指令要大一些。算术逻辑部分主要是译码和操作数选择；乘除法需要额外处理多周期等待和 HI/LO；转移指令要照顾分支的延迟槽；访存指令则需要正确处理字节位置、符号扩展以及非对齐时的新旧数据合并。

在实现和调试中，我感觉比较重要的一点是，每增加一类指令，都要检查它会不会使用前面指令尚未写回的数据。例如 \code{lwl/lwr} 除了写目标寄存器，还会用到它原来的值，如果漏掉这个源操作数，单条指令可能没有问题，连续执行时就容易出错。同样，乘除法的结果即使算对了，如果流水线等待和解除等待的时机不正确，也可能导致后续指令重复执行或跳转错误。

最终，Lab6 的 42 个测试点和 Lab7 的 68 个测试点全部通过，且与独立参考 CPU 的写回记录一致；另外的乘除法单元与相关定向测试也通过。本次结果说明新增指令能够在现有五级流水线中正确运行，并保留原来的阻塞与前递功能。此次主要完成了行为仿真验证，没有进行 FPGA 上板测试。
